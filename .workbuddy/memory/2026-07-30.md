## 新功能：一键下载抓取的静态/文本资源（响应体另存为文件）
- 需求：抓到的 JS（及其它静态资源）响应体，希望能一键另存成本地文件（之前只能看不能单独下载）。
- 后端 `app/server.py`：新增 `GET /api/download?seq=N`。
  - 从 `state.store.get(seq)` 取完整记录，读 `response.body`；无 body 返回 404（二进制未捕获/无 body 的情况）。
  - `_infer_filename()`：文件名取 URL path 末段（如 `src_x.js`）；无扩展名时按 MIME/资源类型补（XHR/FETCH→.json，SCRIPT→.js，STYLESHEET→.css 等）。
  - `_infer_mime()`：优先响应头 Content-Type，否则按资源类型映射。
  - Content-Disposition 同时带 `filename=`（ASCII 兜底）和 `filename*=UTF-8''`（兼容中文名）。
- 前端 `static/app.js`：`renderDetail()` 头部在有 body 时显示「⬇ 下载文件」按钮（`downloadFileBtn`），点击用动态 `<a>` 触发下载（避免弹窗拦截）。
- 验证：py_compile 通过；node --check app.js 通过；Flask test_client 实测 JS 记录返回 200 + 正确文件名/MIME/正文，无 body 记录返回 404；文件名推断覆盖 SCRIPT/XHR/STYLESHEET/中文路径 FETCH 均 OK。
- 注：二进制（图片等）响应体若未被捕获原文则无法下载，属已知限制（用户当前只关注 JS）。

## Bug 修复：下载文件按钮在桌面窗口（pywebview/WebView2）点击无反应
- 现象：详情面板「⬇ 下载文件」按钮点击后无反应；后端日志显示 `GET /api/download?seq=N 200`（请求成功、文件已返回）。
- 根因：pywebview + WebView2 桌面环境下，**网页内的下载动作（`<a download>` / blob / attachment 导航）会被内核静默拦截**（pywebview 未实现下载回调）。初版「动态 a 导航」、二版「fetch+blob」均在此被吞。
- 最终修复：走 pywebview **原生「保存文件」对话框**，由 Python 端写盘，彻底绕过 webview 下载拦截。
  - `main.py`：新增 `RecorderApi` 类，`save_file(filename, content_b64)` 调 `webview.create_file_dialog(webview.SAVE_DIALOG, save_filename=...)` 让用户选路径，base64 解码后写文件；`create_window(..., js_api=RecorderApi())` 暴露给前端。
  - `static/app.js`：监听 `pywebviewready` 构造 ready Promise；下载按钮逻辑改为「fetch 取 blob → base64 → 优先 `window.pywebview.api.save_file`（原生对话框保存），不可用时回退 blob 下载」；保留 loading 态与失败 `alert`。
- 验证：py_compile main.py/server.py 通过；node --check app.js 通过。重启 main.py 生效。
- 注意：保存对话框是**原生系统对话框**，与浏览器默认下载目录无关；用户取消时静默不报错。
- 追加修复：`webview.create_file_dialog` 在该版本 pywebview 中不存在（模块级无此函数），改为 `window.create_file_dialog()`（窗口对象方法）；`RecorderApi` 改为 `_bind(window)` 模式，创建后绑定窗口引用。py_compile 通过。
- 追加修复：`window.create_file_dialog()` 返回 tuple 而非 list，`isinstance(result, list)` 未兜住导致 `open()` 报 `expected str, bytes or os.PathLike object, not tuple`；改为 `isinstance(result, (list, tuple))`。
- 架构简化：前端下载按钮不再 fetch `/api/download?seq=N`，直接用已加载的 `currentDetail.response.body`（前端内存中已有完整数据）→ base64 编码 → 传给 Python 端原生保存对话框写盘。省掉一次网络往返，逻辑更简洁。

## Win7 首次实测修复（DLL 缺失）
- 用户在 Win7 实机双击启动报错「无法启动此程序，因为计算机中丢失 api-ms-win-core-sysinfo-l1-2-0.dll」。
- 根因：之前只从 System32 根目录拷了 api-ms-win-crt-* (15个) + 少量 core，但 Win10 的 **api-ms-win-core-*（Windows 核心 API 转发 DLL）大部分藏在 `System32\downlevel\` 目录**（向下兼容层），共 91 个全漏了。Win7 无 KB2999226 时这些 DLL 不存在。
- 修复：从 `C:\Windows\System32\downlevel\` 补拷全部 91 个 api-ms-win-*.dll 到发布包根目录。现在发布包共 92 个 api-ms-win-*.dll（64 core + 15 crt + 其他），大小 886MB。报错的 `api-ms-win-core-sysinfo-l1-2-0.dll` 已确认在列。
- **教训**：Win7 UCRT 兜底不能只拷 System32 根目录的 crt dll，必须同时拷 downlevel 目录的全部 api-ms-win-* dll（core + crt + base/shell/...），否则 Win7 会缺各种核心 API 转发器。
- **二次修复（真正解决）**：用户反馈补了 92 个 api-ms-win-*.dll 后 Win7 仍报同一错。根因确认：Win7 加载器**不认散落在 exe 同目录的 API-set 转发 DLL**（这些在 Win10 通过系统级 Schema 解析，拷文件到 Win7 当普通 DLL 放没用）。且 DLL 缺失发生在进程加载阶段（早于任何 Python 代码），main.py 的 vc_redist 安装逻辑没机会执行。
- **最终方案**：新增 `启动 API_Recorder.bat` 零依赖启动器——先静默运行 vc_redist.x64.exe（内含完整 UCRT，会正确注册到系统目录），再启动 API_Recorder.exe。装过一次后标记跳过。README 已更新强调「Win7 双击 bat 不要双击 exe」。
- **踩坑：bat 写错路径**：首次用 bash heredoc 写 bat 时变量名误用 `$DIR`（未定义，应为 `$DIST`），导致文件落到错误相对路径而非发布文件夹；且中文文件名在 bash heredoc 有编码问题，文件实际没写进发布包。用户反馈「bat 不在文件夹里」后改用 Write 工具直接写绝对路径解决。教训：写含中文文件名的文件用 Write 工具而非 bash heredoc。
- **三次修复（根因修正 - VC++ 版本不对）**：用户手动跑随包的 vc_redist.x64.exe 后仍报错。根因：**随包的是 VC++ 2022 版，根本不支持 Win7**（VC++ 2022 要求 Windows 10+，在 Win7 上装了等于没装）。正确应为 **VC++ 2015-2019 x64**（最后一个支持 Win7 的版本，内含 UCRT 安装器）。已从 `https://aka.ms/vs/16/release/vc_redist.x64.exe` 下载替换（25MB，存为 `vc_redist_win7.x64.exe`）。
